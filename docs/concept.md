# ことづて(仮)— ハッカソン企画書

> ことづて:人から人へ託されて運ばれる言葉

---

## 前提

- 学生ハッカソン、テーマは自由
- チーム結成は当日、開発期間は実質**3日間**
- 開発は**一人**で行う
- 発表要件(必須):アイデア説明 / プロダクトデモ / GitHubリポジトリ / アーキテクチャ説明 / 工夫した点の説明
- AIの使用は必須ではない(自由)。使うかどうかはコンセプトと評価基準から判断する

---

## 一言で

**ひとつの言葉が、別の誰かの言葉を生んでいく場所。**

偉人の言葉を種火に、心が動いた人が自分の言葉を書く。その言葉は明日、別の誰かに届く。最初は偉人しかいない。でも使われるほど、ユーザー自身が誰かにとっての思想家になる。

---

## 中核:影響の循環

このプロダクトの本質は個別機能ではなく、**ひとつの循環**である。

```
① 言葉が届く(1日1回)
        ↓  心が動いたら
② 自分の言葉を書く
        ↓
③ その言葉が、誰かに届く
        ↓
④ 受け取った人の心が動く
        ↓
①に戻る
```

**このプロダクトは「本を作るアプリ」ではなく「影響が循環する場所」である。**
蓄積(人生本)は循環の結果として生まれるものであり、目的ではない。

### 扱っているのは「思想の伝播」ではない(実装後に整理)

当初は「思想が人から人へ受け渡される」と説明していたが、実際に起きていることは違った。

けんたは、はるかの考えをそのまま受け継いだわけではない。みおも、けんたの考えを受け継いだわけではない。
それぞれが前の言葉に触れて、**思い出したこと・気づいたこと・自分の中で起きた変化**を書いている。

| | 何について書いているか |
|---|---|
| 芥川龍之介 | 危険思想と常識の関係 |
| はるか | 自分が黙ってきたのは、常識のためではなく波風を避けたかっただけ |
| けんた | 会議で黙ることは、賛成したことになっていた |
| みお | 友達の悪口に黙っていた自分 |

端と端で主題がまったく違う。伝わっているのは思想そのものではなく、
**「その言葉がきっかけで何かが生まれた」という事実**である。

これは偶然ではない。書く内容を感想ではなく「自分がどう動いたか」に限定した時点で、
内容は必ず書き手の側に寄る。**内容が変質するのは設計の帰結であって、事故ではない。**

重要なのは「同じ考えが広がること」ではなく「**新しい気づきが生まれること**」。

**発表で避ける表現**:思想の伝播 / 思想を受け渡す / 思想の継承
**使う表現**:影響の循環 / 気づきの連鎖 / 影響の来歴

## 背景・動機

**きっかけになった実体験**
母親から「掃除しろ」「普通はやる」と言われ衝突した。整理すると、これは掃除の問題ではなく、「家=回復空間」という自分の前提と、「家=共同生活の基盤」という母親の前提がズレていただけだった。

**そこから見えた発見**
価値があったのは「母親を理解したこと」以上に、**自分が当たり前だと思っていた前提が、初めて目に見える形になったこと**だった。そしてその気づきは、一人の内省からではなく、**異なる考えを持つ他者に触れたから**生まれた。

**根本にある2つの動機**
- 他人がなぜそう考えるのか、**他者の世界の見え方を覗きたい**
- 自分という存在を消えさせないために、**書き残し、誰かに参照されたい**

この2つは対立しない。**読むから影響を受け、影響を受けたから書く。書いたものが、また誰かに読まれる。** 循環は、この2つの動機が同じ輪の上にあることを形にしたものである。

そして「残す」という動機に対して、このプロダクトが出す答えは**保存ではなく受け渡し**である。倉庫に積まれた記録より、誰かの中に残った一言の方が生き続ける。

---

## 核となる仮説

1. 人は自分の「当たり前」を自分では見られない。見えるのは、違う考えに触れたときだけ
2. 心が動いた瞬間とは、**自分の前提が動いた瞬間**である。だからその時に書かれた言葉は、自動的に「自分が変わった記録」になる
3. 気づきの所有権はユーザーにある。システムが「あなたの前提はこれです」と答えを出してはいけない
4. 思想家とは有名な人のことではなく、**誰かの考えを変えた人**のこと。その定義なら、誰もが思想家になりうる

## プロダクト設計

### ① 言葉が届く(1日1回)

- 1日1回、ランダムに言葉が届く(おみくじのような体験)
- 出典は偉人・思想家の言葉、および**他のユーザーが書き残した言葉**
- 1日1回に制限することで、消費されるコンテンツではなく「今日の一言」としての重みを持たせる

**この機能が解決していること**:検討の初期からずっと未解決だった「**困った時しか開かない**」という問題。悩みがなくても開く理由になり、受け取るだけなら数秒で終わる。

**来歴を一緒に見せる**
届いた言葉がユーザーの言葉である場合、それが何から生まれたかを添えて表示する。

> 今日の言葉:「〜〜〜〜」— たろう
> *この言葉は、たろうさんがニーチェの言葉に触れて書いたものです*

その言葉がどこから生まれたかが、**受け取る瞬間に見える**。これが循環を体験可能にする中核の演出。

### ② 自分の言葉を書く

- 届いた言葉に心が動いたら、自分の言葉を書く
- 書く内容は感想ではなく、**それによって自分がどう動いたか・何に気づいたか**
- 書かなくてもよい(毎日書く義務にはしない)

### ③ 書いた言葉が、誰かに届く

- ①の抽選プールに、偉人の言葉だけでなく**ユーザーが書いた言葉**も含める
- **そして「届いたこと」を本人に見せる**

> あなたの言葉が、今日3人に届きました

これが**このプロダクトの報酬**である。溜まることではなく、渡ることが嬉しい設計にする。

> ⚠️ 設計上の最重要ポイント
> 抽選プールに入れるだけでは、循環は**ピッチの中にしか存在しない**。ユーザーは輪が閉じたことを一生体験できない。「届いた」を可視化して初めて、循環はプロダクトの中で成立する。

### ④ 蓄積(人生本)

- 「届いた言葉 + それに対する自分の言葉」が1ページとして溜まっていく
- ただし**これはホーム画面ではない**。循環が中心であり、蓄積は結果。2番目の画面に置く

### 画面の主従

| | 画面 |
|---|---|
| **ホーム** | 今日の言葉 + 「あなたの言葉が◯人に届きました」 |
| 2番目 | わたしの本(蓄積) |
| 3番目 | 他の人の本を読む |

### 偉人とユーザーの混合比率

抽選時の比率を設計事項として明示的に決める。**初期値は 偉人7 : ユーザー3**。

- ユーザーの言葉が多すぎると、「偉人の言葉に触れる」体験が薄まり、他人のメモを読むアプリになる
- 偉人ばかりだと循環が見えない
- 実装は抽選ロジック数行。体験の質を直接制御できる重要なパラメータ

### やらないこと

- **システムが解釈・断定しない**:「あなたの前提は◯◯です」のような分析結果を出さない。気づくのはユーザー自身であり、その所有権を奪わない
- **議論させない**:コメント・返信・反論・いいねを作らない。SNS的な承認や対立の構造を持ち込まない
- **特定の相手に送らない**:③があれば不要。宛先指定は認証が絡み実装が重くなる

---

## 言葉は枯渇するか(検討済み)

**枯渇しない。構造的に枯渇しえない。**

- プールは在庫ではない。受け取っても言葉は減らない。枯渇は「その人がまだ見ていない言葉が尽きる」という個人単位の話にすぎない
- 300件用意すれば1人が使い切るのに約10か月。デモに必要なのは30〜50件
- **消費より供給が速い**:1人の消費は年365件。しかし100人が年20件書けば年2000件が追加される。使われるほど枯渇から遠ざかる
- 枯れるとしたら、それはコンテンツ不足ではなく**循環が回っていないというシグナル**であり、問題の性質が違う

**将来構想:再会**
同じ言葉が数年後に再び届いたとき、受け取る本人は前と違う人間になっている。
> この言葉は2年前にも届いています。その時のあなたはこう書きました。

実装は既存データを引くだけ。今回は作らないが、蓄積と循環の両方を活かす拡張として語れる。

## 既存サービスとの違い

| | 名言アプリ | SNS | 日記アプリ | 本企画 |
|---|---|---|---|---|
| 集めるもの | 偉人の言葉 | 投稿・反応 | 出来事・感情 | **言葉 + それで自分がどう動いたか** |

初見では名言アプリ・日記アプリに見えるため、ここを最初に潰す。

## MVP:3日間で作る範囲

| 段階 | 3日間で | 備考 |
|---|---|---|
| ① 言葉が届く | **作る** | 体験の入口。デモの第一手 |
| ①' 来歴の表示 | **作る** | JOIN1回。循環が見える演出の核 |
| ② 自分の言葉を書く | **作る** | 核。省けない |
| ③ 誰かに届く + **届いた表示** | **作る** | 抽選プール数行 + 件数表示数行。**循環の主張そのものなので削らない** |
| ④ 人生本として溜まる | **作る** | 2番目の画面 |
| ⑤ 他人の本を読む | **作る(閲覧のみ)** | 一覧+閲覧だけ。数冊あれば成立 |

**③を削ってはいけない理由**:③は機能ではなく主張そのもの。削ると、まさに警戒している「名言アプリ+日記」になる。しかも実装は数行と安い。演出に時間を使うより投資効率が高い。

**演出の優先順位**:①受け取りの演出 > ③届いたことの演出 > ④ページが増える演出

### スコープ外
- コメント・返信・いいね等のSNS的機能
- 認証・アカウント管理の作り込み(ニックネーム程度で十分)
- AIによる前提の抽出・解釈(「システムは解釈しない」方針のため)
- 特定の相手に言葉を送る機能
- 統計・グラフ・分析画面

## AIを使うかどうか

**必須ではないため、無理には使わない。** 本企画の方針は「システムが解釈しない」ことであり、AIに前提を言語化させる設計はこの方針と矛盾する。

使う場合の候補(いずれも任意・時間が余った場合):
- 今日届ける言葉の選定を、直前に書いた内容と響き合うものにする(単純ランダムではなく意味的な選択)
- 不適切な投稿のフィルタリング

**「AIを使わない理由を説明できること」自体が強みになる。**

## 技術スタック

| 領域 | 選択 | 理由 |
|---|---|---|
| フレームワーク | Next.js (App Router) | フロント/バックを1プロジェクトで完結 |
| スタイリング | Tailwind CSS | 短時間で見た目を整えられる |
| データ保存 | 軽量DB(Supabase等) | 言葉・ページ・配信履歴を保持し、他人の本を読むために共有が必要 |
| デプロイ | Vercel | 数分でデプロイでき、当日のURL共有も容易 |
| LLM(任意) | Claude API / OpenAI API | 使う場合のみ |

### データ構造(アーキテクチャ説明用)

```
words(届く言葉)
  - id
  - text             … 言葉本文
  - author           … 偉人名 or ユーザー名
  - source_type      … "classic"(偉人) / "user"(ユーザー)
  - source           … 出典(偉人の場合)
  - source_url       … 出典URL(偉人の場合)
  - original         … 原文(原典から訳出したもの)
  - translation_note … 訳出の注記
  - author_user_id   … 書いた人(ユーザーの言葉。偉人はnull)
  - parent_word_id   … この言葉を生んだ言葉(来歴。偉人はnull)
  - created_at

deliveries(配信履歴)
  - id
  - user_id         … 届けた相手
  - word_id         … 届けた言葉
  - delivered_at

users
  - id
  - nickname
  - created_at
```

**この構造が実現していること**

1. **偉人とユーザーが同じテーブルに同じ形式で並ぶ**(`words`)。「思想家とは有名人ではなく誰かの考えを変えた人である」という思想が、データ構造そのものに埋め込まれている
2. **`parent_word_id` が影響の来歴を保持する**。継承ではなく「この言葉がなければ、この言葉は生まれなかった」を記録している。ニーチェ → Aさん → Bさん → あなた、という連鎖を辿れる
3. **`deliveries` が3つの役割を同時に果たす**:同じ言葉を同じ人に重複配信しない / 「あなたの言葉が◯人に届きました」を数える / 循環が実際に回っている証跡になる

**`pages` テーブルを持たない理由(実装時の判断)**

検討段階では「人生本の1ページ」を独立したテーブルにする想定だったが、実装時に取りやめた。
1ページは「自分が書いた言葉」と「その `parent_word_id`」で完全に表せるため、`pages` を置くと
`words` と同じ内容を二重に持つことになる。テーブルを1つ減らし、`words` から導出する形にした。

## 工夫した点(発表用)

1. **機能の集合ではなく、ひとつの循環として設計した**:受け取る・書く・届く・また誰かが受け取る、が1本の輪になっている
2. **報酬を「溜まること」ではなく「渡ること」に置いた**:抽選プールに入れるだけでは循環はピッチの中にしか存在しない。「届いた」を可視化して初めてユーザーが輪を体験できる、という設計判断
3. **あえて解釈させない**:システムが「あなたはこういう人です」と分析する実装の方が簡単だが、それをやらない。気づきの所有権をユーザーに残すため
4. **偉人とユーザーを同じテーブルに置いた**:データ構造そのものが「誰もが思想家になりうる」という思想を表現している
5. **議論の構造を持ち込まなかった**:コメントも返信もいいねもない。SNS的な対立と承認から意図的に距離を置いた

## 想定質問と回答

**なぜ1日1回なのか?**
SNSは大量消費される情報ですが、このプロダクトは情報消費ではなく内省のきっかけを作ることが目的です。そのため無限スクロールではなく、あえて1日1回にしています。

**他人の本を読む意味は?**
自分の前提は自分では見えません。違う考え方に触れることで初めて、自分との差分に気づけると考えています。

**AIを使わないのか?**
気づきの所有権をユーザーに残したかったためです。システムが「あなたはこういう人です」と解釈するのではなく、ユーザー自身が気づくことを重視しています。

**言葉が枯渇しないか?**
プールは在庫ではなく、受け取っても減りません。さらにユーザーが書くほどプールは増えるため、使われるほど枯渇から遠ざかります。

**名言アプリとの違いは?**
集めるのは名言ではなく「言葉と、それによって動いた自分」です。そしてその言葉が次の誰かに届くという循環がある点が根本的に異なります。

## デモシナリオ(3分想定)

1. **課題提示**:「自分の当たり前って、自分では気づけないですよね。気づくのは、違う考えに触れた時だけです」
2. **前置き**:「このサービスが集めるのは名言ではありません。言葉と、それによって動いた自分です」
3. **今日のことづてを受け取る**:1つの言葉が届く場面。**来歴付き**で見せる(ニーチェ → Aさん → Bさん、と辿れる様子)
4. **その場で書く**:心が動いたことを実際に書き、託される瞬間を見せる
5. **届いた報せを見せる**:「あなたの言葉が◯人に届きました」
6. **他人の本を開く**:他の人がどんな言葉に動かされたかが見える
7. **締め**:「今この場で私が書いたこの言葉が、明日、誰かのもとに届きます」
8. 最後に実体験(母親との衝突)に触れて終える

**事故防止**:バックアップ動画を事前録画。当日のネットワーク不調に備える。

## リスクと対策

**1. 引用の捏造(最重要)**
LLMに「偉人の名言を生成させる」と、**存在しない引用を平気で捏造する**。誤帰属はネット上の名言botでも蔓延しており、審査員に見抜かれると信用を大きく損なう。
→ 青空文庫などパブリックドメインの一次資料、または出典が明確なものを**手動で**30〜50件用意する。AIに名言を作らせない。

**2. 著作権**
存命の作家・現代の著述家の言葉は避ける。
→ 著作権切れの古典に限定し、「出典が明確なパブリックドメインの言葉のみを使用」と明言できる状態にする。

**3. 「名言アプリ+日記」に見えるリスク**
→ 発表冒頭で「集めるのは名言ではなく、言葉と動いた自分」と明示。加えて循環(③)を必ず見せる。

**4. 不適切な投稿がランダム配信される可能性**
ユーザーの言葉を抽選プールに入れる以上、理論上は起こりうる。
→ デモでは実質問題にならないが、「本番運用では公開前フィルタを入れる」と回答を用意する。

## 確定した検討事項

| 項目 | 決定 | 理由 |
|---|---|---|
| プロダクト名 | **ことづて** | 「受け渡し」という中核と意味が一致し、説明が1行で済む |
| ユーザー識別 | **匿名ID + ニックネーム** | 初回にニックネームだけ受け取り、cookie に id を保持。メールもパスワードも扱わない。認証UIに時間を使わない |
| 人生本の公開範囲 | **全公開** | 実装が最も軽く、「渡ること」という思想とも一致する。⑤他の人の本が必ず中身を持つ |
| 引き直し | **本番は不可** | 1日1回の重みを守る。`ALLOW_REROLL=true` のときだけ解除し、開発とデモに使う |
| 混合比率 | **偉人7:ユーザー3** | `CLASSIC_RATIO` 環境変数で調整できるようにし、触りながら決められる状態にした |

### 残っている検討事項
