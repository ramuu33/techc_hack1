# 前提の交換所(仮)— ハッカソン企画書(最終版)

## 前提
- 学生ハッカソン、テーマは自由
- チーム結成は当日、開発期間は実質**3日間**
- 開発は**一人**で行う
- 発表要件(必須):アイデア説明 / プロダクトデモ / GitHubリポジトリ / アーキテクチャ説明 / 工夫した点の説明

---

## 一言で

お互いが投稿するたびに、自分も相手も、自分では気づかなかった前提に気づける。そして2人の前提を並べると、一致している部分とズレている部分が見えてくる。

---

## 背景・動機

**きっかけになった実体験**
母親から「掃除しろ」「普通はやる」と言われ衝突した。整理すると、これは掃除の問題ではなく、「家=回復空間」という自分の前提と、「家=共同生活の基盤」という母親の前提がズレていただけだった。

**そこから見えた、より本質的な発見**
価値があったのは「母親を理解したこと」以上に、「自分が当たり前だと思っていた前提が、初めて自分の目に見える形になったこと」だった。そして、この気づきは一人で内省して得たものではなく、**自分と異なる前提を持つ他者(母親)と対比したからこそ**得られたものだった。

**自分自身の興味の再発見**
検討を重ねる中で、自分は「自分探し」よりも「他人がなぜそう考えるのか、他者の世界の見え方を覗くこと」に昔から興味があったと気づいた。この企画で本当に活かすべきは、自己分析ツールとしての側面ではなく、**この"覗く"面白さ**だった。

---

## 核となる仮説

1. 人は自分の前提(当たり前)に自分では気づけない
2. 前提は、一人の内省よりも、**自分と異なる前提を持つ他者との対比**によって見えやすくなる
3. 「他者の世界の見え方を覗きたい」という欲求と、「自分の前提に気づきたい」という欲求は、双方向のやり取りの中でどちらも満たせる
4. 一方が他方を分析するのではなく、**お互いが投稿し、お互いが気づきを得る**設計にして初めて、倫理的にも体験的にも成立する

---

## プロダクト設計

### 基本構造:1対1・双方向

オープンな公開SNSではなく、**特定の1人の相手と、閉じた形でやり取りする**。オープンな交換所は「コールドスタート問題」(投稿者がいないと成立しない)があり、3日間・一人開発のハッカソンでは現実的でないため。

### やり取りの流れ

1. 自分が、モヤモヤや気づきを自由記述で投稿する
   例:「友達と旅行すると疲れる」
2. AIがその投稿の裏にある前提候補を抽出する(根拠付き、断定しない)
   例:「一人で意思決定したい」「移動は休息ではなく消耗」
3. 相手にも同じように投稿してもらう
   例:「旅行は共同体験だと思う」
4. 2人の前提を並べて表示する。**一致している部分**と**ズレている部分**の両方を見せる

### AIの役割

AIは「アドバイスする」「断定する」のではなく、**投稿の裏にある前提候補を、根拠とともに提示する**役割に徹する。第三者の心理を無断で推測するのではなく、**本人が実際に書いた投稿のみ**を根拠にする。相手についても、相手自身が書いた投稿から前提を抽出するので、無断推測の倫理的懸念が生じない。

### なぜ双方向にするか(価値設計)

- 投稿した本人も、自分では気づかなかった前提に気づける(自分にとっての価値)
- 相手の投稿と並べることで、他者の世界の見え方を覗ける(覗く面白さ)
- 相手にとっても「自分は覗かれるだけ」にならない。相手も投稿することで、相手自身も気づきを得られる(双方に価値がある設計)

## 既存サービスとの違い

| | 性格診断・相性診断 | SNS | 本企画 |
|---|---|---|---|
| 根拠 | 決まった質問への回答 | 投稿された意見・出来事 | 実際の投稿から抽出された前提 |
| 焦点 | 固定的なタイプ分類 | 出来事・意見そのもの | なぜそう考えるか、という前提 |
| やり取り | 一方向(診断結果を見るだけ) | 意見への反論・いいね | 前提を並べるだけ(議論させない) |

**差別化のために厳守すること**:反応の形式を「反論・共感コメント」にしない。あくまで前提を並べて見せるだけに留め、議論の場にしない。ここを崩すと、単なる意見投稿SNSと差がなくなる。

---

## MVP機能

1. 投稿入力欄(自由記述)
2. AIによる前提候補の抽出+根拠(投稿のたびに)
3. 招待した相手も同じ画面で投稿できる(シンプルな共有リンク方式、認証不要でよい)
4. 2人分の前提を並べて表示(一致点・相違点)

### スコープ外(3日間では作らない)
- オープンな公開交換所(誰でも投稿できる形)
- 診断カードのゲーム化・コレクション演出
- 議論・コメント・いいね等のSNS的機能
- 3人以上のグループ比較(まずは1対1に絞る)
- 複雑な認証・アカウント管理

## プロンプト設計方針

```
あなたは、ユーザーの投稿から「本人も気づいていない前提・当たり前」を
見つけ出す手伝いをします。

【ルール】
- 断定せず、あくまで候補として提示すること
- 提示した前提がどの記述から推測されたか、根拠を示すこと
- 本人が実際に書いた内容のみを根拠にし、それ以上の深読みをしないこと

【入力】
{ユーザーの投稿}

【出力形式(JSON)】
{
  "前提候補": "...",
  "根拠": "..."
}
```

**工夫点として語れるポイント**
- 一方が他方を分析するのではなく、双方が投稿することで、倫理的な懸念(無断で他者の心理を推測すること)を回避している
- 反応の形式を「前提を並べるだけ」に制限し、議論・反論を発生させない設計にすることで、SNSとの差別化を保っている

## デモシナリオ(3分想定)

1. 課題提示:「自分の"当たり前"って、自分では気づけないですよね。しかも、それに気づくのは大抵、誰かと考え方が違ったときです」
2. 自分の投稿を入力し、AIが前提候補を抽出する瞬間を見せる
3. あらかじめ用意しておいた「相手役」の投稿と並べ、一致点・相違点が表示される様子を見せる
4. 「これは家族との衝突から生まれたアイデアです」と実体験に触れ、締める

## 3日間のスケジュール

| 日 | 内容 |
|---|---|
| **Day1** | 環境構築、投稿→AI前提抽出のコア機能実装、プロンプト設計・検証 |
| **Day2** | 2人分のデータを紐づけて比較表示する機能(共有リンク含む)を実装、UI/UXを整える |
| **Day3** | README・アーキ図作成、デモシナリオ作り込み、バックアップ動画撮影、リハーサル、バッファ |

## 第三者レビューで指摘された点

- 実体験からの一般化・双方向設計・「助言しない」AIの役割制限は、既存の診断/SNS/相談AIとの差別化として筋が通っている、と評価された
- **最大のリスクはAI精度**:「前提候補」の抽出と「一致/近い/ズレ」の判定がAI任せだと当たり障りのない/的外れな出力になりやすい。3日間でデモに耐える精度を出せるかが肝
- 対策として、Day1のうちに実データ(自分の投稿)でプロンプトを検証し、「使える手応え」があるか早期に確認すべき
- 「判定の粒度」はUXより先に、Day1中に決めるべき(後工程がぶれるため)

## 判定の粒度(決定事項)

**案A:2つの前提テキストをまとめてLLMに都度判定させる方式を採用**
- 理由:3日間の制約下では実装が速く、Day1の精度検証にもそのまま使える
- 見送った案(案B):前提を軸(カテゴリ)ごとに分類してから比較する方式。意味の通った比較になりやすいが、軸設計のコストが高く3日間では見送り。時間が余れば後から拡張候補とする

## Day1で行う精度検証(具体タスク)

1. 自分の過去の投稿・出来事を5〜10個用意する(例:「親に掃除しろと言われて腹が立った」「友達と旅行すると疲れる」など)
2. それぞれに前提抽出プロンプトを適用する
3. 「これは自分でも気づいていなかった」と思えるものが半分以上出るかを基準に判定する
4. 基準に満たない場合、根拠(投稿内の具体的な言葉)をどれだけ拾えているかを軸にプロンプトを調整する

**プロンプトの試作結果(会話内で試行)**
- 入力例:「親に掃除しろと言われて腹が立った」→ 前提候補「自室は管理対象ではなく、心身を回復させるための領域だと考えている」
- 入力例:「友達と旅行すると疲れる」→ 前提候補「移動や外出は、休息ではなく気力を消耗する行為として捉えている」
- 手応え:根拠が投稿文の具体的な言葉を拾えているかどうかが、当たり障りのない一般論に落ちるかの分かれ目になる
